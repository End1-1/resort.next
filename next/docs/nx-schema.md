# Схема nx_

Решение владельца: хранилище `next/` — новая схема с нуля, все таблицы с префиксом `nx_`. Идеи сущностей взяты из [docs/audit/02-baza-dannyh.md](../../docs/audit/02-baza-dannyh.md) §2.3, имена другие. Expand/contract из §2.4, который оставлял `f_reservation` и `m_register` долгосрочным хранилищем и совместимыми view, на этот API не распространяется.

Старые таблицы не меняются этой миграцией и не являются источником правды для `hotel-api`. `legacy_id` на части строк — необязательный ключ будущего копирования, не внешний ключ на старую таблицу.

DDL: [`next/dbdump/migrations/0002_nx_core.sql`](../dbdump/migrations/0002_nx_core.sql).

Кодировка `utf8mb4` / `utf8mb4_unicode_ci`, движок InnoDB, суррогатный `bigint`, внешние ключи между таблицами `nx_`. Деньги — `decimal(14,2)` плюс код валюты и знак, не пара колонок AMD/USD.

`0001_hotel_api_session.sql` сервис больше не создаёт и не читает. Новой базе он не нужен.

## Применение

Из корня репозитория, в ту базу, куда смотрит DSN (`dsn` в `hotel-api.ini` или непустой `HOTEL_DSN`):

```bash
mariadb --default-character-set=utf8mb4 -h HOST -u USER -p DATABASE \
  < next/dbdump/migrations/0002_nx_core.sql
```

Повторный запуск дописывает только справочник `nx_voucher` (`ON DUPLICATE KEY UPDATE`). `CREATE TABLE IF NOT EXISTS` не чинит таблицу, которая создалась наполовину. Если первый прогон оборвался, удалите появившиеся таблицы `nx_*` и выполните файл снова, пока в них нет данных.

Сборка сервиса после миграции — в [next/server/README.md](../server/README.md).

## Вход и сид

`POST /api/v1/sessions` читает `nx_user` и пишет `nx_session`. Таблицу `users` запрос входа не трогает.

Переходный пароль — это формат хеша в `nx_user`, не чтение старой колонки на каждый логин: `password_scheme = 'md5'`, `password_hash` — 32 hex-символа MD5 от UTF-8 пароля (те же байты, что у десктопа). Других схем этот бинарник не проверяет и хеш назад не переписывает.

Строки пользователей миграция не вставляет. Шаблон ручного сида, без настоящих секретов: [`next/dbdump/seed/nx_user.example.sql`](../dbdump/seed/nx_user.example.sql). Там же комментарий, как один раз скопировать активные логины из `users`, если это нужно на сервере. Дубликаты `f_username` надо разобрать до копирования: на `nx_user.login` стоит `UNIQUE`.

`commands_allowed` истинен, когда у роли есть хотя бы одна строка `nx_role_permission`. Пустой список прав вход не запрещает: токен выдаётся, командного маршрута в этом билде нет.

В ответе `user.role_id` — это `nx_role.id` (или null). Поле `user.group` повторяет то же число, чтобы клиент 0.2 по-прежнему видел ключ.

## Старое → nx_

| Было | Стало | Что изменилось |
|------|--------|----------------|
| база целиком как один объект | `nx_property` | код, часовой пояс, валюта учёта |
| `f_room_building` | `nx_building` | корпус внутри объекта |
| `users` | `nx_user` | `UNIQUE` на логин, схема пароля отдельной колонкой |
| `users_groups` | `nx_role` | код роли уникален в пределах объекта |
| `users_rights`, `users_rights_template` | `nx_permission`, `nx_role_permission` | право с именем, одна выдача на пару роль+право |
| `s_user_session`, `web_sessions`, `hotel_api_session` | `nx_session` | хеш токена, срок UTC, `revoked_at` без нулевой даты и без `ON UPDATE` на времени входа |
| `f_guests` | `nx_guest` | гость объекта; документ пока одной колонкой |
| `f_room_classes` | `nx_room_type` | код типа уникален в объекте |
| `f_room` | `nx_room` | тип и корпус — внешние ключи, номер уникален в объекте |
| шапка `f_reservation` | `nx_reservation` | источник/канал и статус брони, без тарифа и состава гостей в той же строке |
| номер, даты, `f_state`, pax | `nx_stay` | отрезок проживания; группа — несколько stay на одну бронь |
| `f_reservation_guests` | `nx_stay_guest` | гость на отрезке; состав брони — гости её stay |
| смысл фолио (`f_invoice` на брони) | `nx_folio` | счёт брони или отрезка; баланс колонкой не хранится |
| `m_register` | `nx_posting` | сумма, валюта, знак, код ваучера; отмена — новая строка (`reverses_posting_id`) |
| `m_vaucher` | `nx_voucher` | `UNIQUE` на код (старые дубли `RR` и `CM` сюда не переносятся) |
| `f_global_settings` | `nx_setting` | один ключ на объект, не мешок EAV без уникальности |

Справочник кодов ваучера в миграции — это каталог (`AV`, `RM`, `RV`, …), не данные гостей. Флаги `affects_balance` и `requires_payment` лежат в таблице для будущего сервиса проводок. Сам сервис проводок не пишет.

## Чего в этом файле нет

Ресторан, склад, фискальный чек, сезоны тарифов, задачи горничных, отчёты с SQL, телефонная станция. Правил фолио в `hotel-api` нет: таблицы `nx_folio` и `nx_posting` есть, HTTP-маршрута нет.

Пересечение двух stay по одному номеру и датам схема не запрещает. Пароли ККМ в `nx_setting` не класть.
